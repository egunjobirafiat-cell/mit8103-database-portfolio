1. Selected Case Study Overview

The chosen case study is the Riverside University Student Result Portal (Simulated). The system provides transactional data management and query access for three primary stakeholder groups:

  • Students: Register for semester course sections, monitor recorded continuous assessment marks, calculate semester GPAs, and retrieve end-of-term academic transcripts.
  • Lecturers: Access class enrollment rosters for assigned sections and submit final student scores (0–100).
  • Registry Staff: Maintain academic departments, configure courses (1–6 credits), schedule offerings (sections), and supervise student enrollment.

2. Technical Deliverables across Portfolio Activities

Activity 1: Database Design and Modelling

The relational schema is implemented in standard SQL (schema.sql) across seven tables: department, student, lecturer, course, term, offering, and registration.

  • Composite Primary Key: The registration table enforces a composite primary key (student_id, offering_id), preventing duplicate registrations. Foreign key integrity is enabled via PRAGMA foreign_keys = ON.
  • Domain Constraints: Validated via check constraints: CHECK (credits BETWEEN 1 AND 6), CHECK (section > 0), and CHECK (score IS NULL OR (typeof(score) = 'integer' AND score BETWEEN 0 AND 100)). Uniqueness of class sections within a term is guaranteed via UNIQUE (course_id, term_id, section).
  • Normalisation (1NF to 3NF): All fields hold atomic values (1NF); the non-key attribute score is fully functionally dependent on the composite key {student_id, offering_id} with no partial dependencies (2NF); department, course, and instructor metadata are isolated into reference relations, removing transitive dependencies (3NF).
  • Integrity Verification: Executing run.py intentionally attempted duplicate registrations, scores > 100, and non-existent student IDs. All were actively rejected by the SQLite engine: 
    Rejected: UNIQUE constraint failed: registration.student_id, registration.offering_id
Rejected: CHECK constraint failed: score IS NULL OR (typeof(score) = 'integer' AND score BETWEEN 0 AND 100)
Rejected: FOREIGN KEY constraint failed
Rejected: CHECK constraint failed: typeof(credits) = 'integer' AND credits BETWEEN 1 AND 6

Activity 2: Query Processing, Optimisation and GPA Calculation

Evaluated a high-frequency grade roster query that retrieves all graded student registrations for an assigned course offering across 50,000 synthetic records: 

SELECT student_id, score FROM registration WHERE offering_id = ? AND score IS NOT NULL ORDER BY student_id;
  • Baseline Execution (Before Indexing): Using only the composite primary key (student_id, offering_id), SQLite could not perform a direct B-tree search on offering_id because student_id was the leading key. It executed a full index scan of all 50,000 entries: 
    Plan: [(4, 0, 218, 'SCAN registration USING INDEX sqlite_autoindex_registration_1')]
Result: 500 rows | Median execution time (11 runs): 3.876 ms
  • Covering Index Design: Created a composite index: CREATE INDEX registration_roster ON registration(offering_id, student_id, score);. offering_id satisfies the equality filter via a logarithmic B-tree search (O(log N)); student_id satisfies the sort order; score covers the projection and NOT NULL predicate.
  • Optimised Execution: All requested attributes were satisfied directly from index leaf pages with zero table lookups: 
    Plan: [(3, 0, 56, 'SEARCH registration USING COVERING INDEX registration_roster (offering_id=?)')]
Result: 500 rows | Median execution time: 0.459 ms (~8.4x speedup / 88.2% latency reduction)
  • Semester GPA Calculation: Addressing the key operation on Page 2 of the brief, a GPA calculation query was implemented in gpa_calculation.sql based on the Nigerian 5.0 scale (A=5, B=4, C=3, D=2, F=0). For Student 100 across 3 courses (8 credit units), the system computed 32.00 quality points, yielding a verified semester GPA of 4.00 / 5.00.

Activity 3: Transactions and Concurrency

Configured SQLite under Write-Ahead Logging (PRAGMA journal_mode = WAL) and tested concurrent database interactions using two independent connections (writer and reader) with zero lock timeout:

  • Snapshot Isolation & Repeatable Reads: The reader opened an explicit transaction (BEGIN) and recorded student 100's score (52). While the read transaction remained open, the writer initiated BEGIN IMMEDIATE, updated score to 85, and committed. The reader queried again inside the same open transaction and consistently observed 52, proving in-flight snapshot repeatability. Once the reader completed its transaction, a fresh read observed 85.
  • Writer Contention: While the writer held the write lock, the reader attempted BEGIN IMMEDIATE, which was rejected with OperationalError: database is locked (SQLITE_BUSY), validating single-writer lock serialization.
  • Commit & Rollback: Once the writer committed, the reader immediately observed 85. A subsequent uncommitted score update was followed by ROLLBACK; the reader verified the score remained intact at 85 (Atomicity).

Activity 4: NoSQL and Document Data Model

In 3NF, rendering a semester transcript requires joining four tables (registration JOIN offering JOIN course JOIN term), causing server strain during exam results release. To optimize reads, a document store was implemented using SQLite's JSON extension:

  • Document Schema (Single Course Excerpt): Transcripts are stored as pre-materialized JSON documents under key student:{id}:term:{term_id} with RFC-8259 syntax enforced by CHECK (json_valid(body)) (excerpt shown; full document in run.py contains all 3 semester courses): 
    {
  "student_id": 100, "term": "2026/2027 Semester 1",
  "results": [{ "course": "MIT8103", "title": "Advanced Database Systems", "section": 1, "score": 85 }]
}
  • Extraction Query: Embedded marks were retrieved without relational joins using table-valued JSON functions: 
    SELECT json_extract(result.value, '$.score') FROM transcript, json_each(transcript.body, '$.results') 
WHERE transcript.id = 'student:100:term:1' AND json_extract(result.value, '$.course') = 'MIT8103';  -- Returns [(85,)]
  • Trade-off Evaluation: Fetching the full document is a direct primary key B-tree index seek (O(log N) in SQLite; O(1) in dedicated key-value stores like Redis), bypassing relational joins entirely. In exchange, course titles are duplicated across documents, requiring an asynchronous event worker to refresh cached documents if course titles change.

Activity 5: Distributed and Cloud Database Architecture

  • High Availability & Multi-AZ: Designed a cloud deployment using managed Amazon Aurora Multi-AZ clustering (PostgreSQL/MySQL Compatible) with a Primary instance in AZ-1 and a Synchronous Standby in AZ-2. Synchronous distributed storage quorum replication ensures zero data loss (RPO = 0) and automated failover in under 30–60 seconds (RTO < 60s, substantiated by Aurora's shared storage layer compared to 60–120s for traditional RDS instances).
  • Read Scaling & Replication Lag: Asynchronous read replicas handle student transcript reads. To prevent the "read-your-own-writes" inconsistency (where an instructor submits marks and sees stale data upon immediate refresh), post-submission reads are pinned to the Primary node for 5–10 seconds, combined with Log Sequence Number (LSN) causal tracking for monotonic consistency during replication lag spikes.
  • Sharding & Disaster Recovery: Evaluated campus-level vs student-hash sharding; recommended keeping active academic terms centralized on an Aurora cluster and archiving past graduated terms into object storage. Continuous Write-Ahead Log (WAL) streaming to Amazon S3 enables Point-in-Time Recovery (PITR).

3. Individual Technical Reflection

Index Column Ordering: Completing Portfolio 2 demonstrated that simply having an index on a table does not make every query fast. Because the composite primary key started with student_id, queries filtering by offering_id were forced into full scans. Designing the covering index (offering_id, student_id, score) aligned index leaf order with filter and sort predicates, cutting median query time from 3.876 ms to 0.459 ms.

Concurrency Realities: The WAL experiment showed the practical boundary between concurrency and locking. While SQLite WAL provides non-blocking reads, its single-writer limit surfaces database is locked under write contention. In an enterprise university deployment with hundreds of lecturers submitting grades simultaneously, an engine like PostgreSQL with row-level locks (FOR UPDATE) and optimistic concurrency control would be preferred.

Polyglot Persistence: The document exercise illustrated why modern architectures use hybrid persistence: relational databases serve as the ACID-compliant System of Record for grade recording, while document stores serve as read-optimized materialized views for instant transcript rendering.

Distributed Architecture Trade-offs: Evaluating multi-AZ cloud deployments highlighted the fundamental CAP theorem constraints. Synchronous replication to a standby AZ guarantees RPO = 0 but introduces network transit latency on commit paths. Offloading read workloads to asynchronous replicas resolves web-tier contention but necessitates application-level mitigation (such as session pinning for grade submission workflows) to guarantee read-your-own-writes consistency.
